# Concept: Multi-Agent Team（多 Agent 团队）

一个领导（lead）拿目标拆活，派给几个各带独立 [[Context]] 的成员，成员分头干完交回压缩过的结论，lead 汇总并对最终产物负责。

**和单个 [[Agent]] 的差别**：差别落在上下文容量与并行度上——它能同时摊开几个窗口去想，模型本身没有变聪明。Anthropic 的归因很清楚——token 用量单独解释 80% 的性能方差，团队成员本质上是"多开几个窗口去花 token"。

**四部件**：团队领导、成员、共享任务板（可认领、可设依赖）、信箱（成员间直连，能绕开领导）。

**第一判据：读出并发，写入串行。**
- 只读且互不依赖的步骤（检索、核实、读文件、代码搜索）可以并行，最坏结果是取到重复数据。
- 写操作（改文件、提交、定规范、统一风格）必须串行。两个人同时写同一份产物就是互相覆盖，症状是"每段都合理、整体不协调"。

**成本门槛**：单 agent 约 4 倍聊天 token，多 agent 约 15 倍。任务价值撑不起这个溢价时，一个会话就够了。

**同预算下的反证**：Tran 与 Kiela（arXiv:2604.02460）把 token 预算对齐后，单 agent 在多跳推理上稳定打平或超过多 agent，理论依据是数据处理不等式——每转交一次只能丢信息。所以多 agent 的适用面是"上下文碎片化"，推理深度型任务交给单 agent 更划算。

**两派立场与和解**
- [[Anthropic]] 2025-06：orchestrator-worker，Opus 4 + Sonnet 4 子代理比单 Opus 4 高 90.2%，代价 15 倍 token。
- [[Cognition]] 2025-06：两条原则——共享上下文与完整轨迹；动作携带隐性决策。默认推荐单线程线性 agent。
- [[Cognition]] 2026-04 自我修正：写在单线程时多 agent 可行，形状是 map-reduce-and-manage；独立审查者用干净上下文效果更好。
- 和解后的规则：并行化阅读与思考，串行化写入。额外 agent 在"收集上下文、提供判断"时值钱，一旦两个 agent 写同一个产物就开始亏。

**常见误区**
- 人多力量大：同质采样投票呈倒 U 形，超过阈值后冗余候选稀释有效性。
- 自由群聊能涌现协作：纯自然语言多轮传递必然失真，交接要有结构化产物。
- 多 agent 是质量保险：MAST 归纳的失败集中在协作结构（角色边界、中间验证、目标错位），加人只会放大结构问题。

**何时别拆**：任务顺序强依赖、子任务要共享未写下来的风格约定、价值撑不起 15 倍成本、一个会话能收尾。
