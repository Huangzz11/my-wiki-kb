# 多 Agent 团队：它是什么，值不值，什么时候该拆

## 1. 学习目标

读完能回答三个问题：

1. 一个"多 agent 团队"和"一个 agent 多调几个工具"的界线划在哪。
2. 什么样的任务值得为它付大约 15 倍的 token。
3. 手上这套内容生产的活（选题、核查、出图、复查），该拆成几个成员、谁负责写。

## 2. 一句话理解

一个 lead 拿着目标和一块共享任务板，把活拆给几个各带独立上下文窗口的成员，成员分头干完把**压缩过的结论**交回来，lead 汇总，并对最终产物负责。

打个比方：像带一个外包小组做行业报告。主编定框架、分章节、最后统稿；调研员各跑一个方向，只交"结论 + 出处"，不把过程全搬回来。这份活搞砸通常有两个原因——分活时没说清边界，或者两个人同时改同一段稿子。

三句话记住它：

- 团队解决的是**上下文容量**和**并行时延**，跟"让模型变聪明"没关系。
- 收益来自结构（角色边界、中间产物格式、拓扑），跟人数没关系。
- 读可以并行，写必须单线程。

## 3. 核心机制 / 组成

### 3.1 三个部件

| 部件 | 干什么 | 缺了会怎样 |
|---|---|---|
| 团队领导 Team Lead | 拆任务、派活、审计划、汇总、对最终结果负责 | 没人统稿，成员产出拼不起来 |
| 成员 Teammates | 各自独立的会话实例，独立上下文窗口，独立工具权限 | 退化成一个 agent 顺序干活 |
| 共享任务板 + 信箱 | 任务可认领、可设依赖；成员之间能直接发消息 | 靠 lead 中转，协调开销翻倍 |

关键在于成员的上下文是**隔断**的。WorkBuddy 的 Agent Teams 文档写得很直白：成员会加载项目上下文（项目说明、MCP、技能），但**不会继承领导的对话历史**。好处是每个成员的工作记忆不会被别人的探索过程污染；代价是你必须把任务背景写进初始 prompt，写不全它就猜。

### 3.2 三种拓扑

- **放射状（orchestrator-worker）**：lead 拆、成员并行、lead 收。Anthropic 的 Research 功能走这条。子任务互不依赖时最快。
- **网状（peer / 群聊）**：成员之间直接对话、互相质疑。WorkBuddy Agent Teams、AutoGen 的 GroupChat、CAMEL 的角色扮演属于这类。适合竞争性假设、需要辩论的场景，协调开销最大。
- **层级（hierarchical）**：管理层再管一层。CrewAI 的 hierarchical 流程、Microsoft Agent Framework 都支持。成员多到十几个才值得。

有个反直觉的点：网状拓扑听起来更"智能"，2025 年之后工程界的判断恰恰相反。Cognition 的原话是，任意 agent 互相协商的非结构化 swarm"基本是个干扰项"，能跑通的形状是 map-reduce-and-manage——经理拆、子代跑、经理合成。

### 3.3 一场持续一年的立场修正

这个领域最有价值的部分是两篇几乎同周发布的文章互相打脸，然后又自己和解。

| 时间 | 谁 | 主张 |
|---|---|---|
| 2023-08 | MetaGPT（ICLR 2024 Oral） | 把人类软件公司的 SOP 编码进提示序列，角色分工 + 结构化中间产物（PRD、设计文档）能压住"级联幻觉" |
| 2025-03 | Cemri 等《Why Do Multi-Agent LLM Systems Fail?》 | 7 个主流框架、1600+ 条标注轨迹，归纳出 14 种失败模式、3 大类；摘要直言"在流行基准上的性能增益往往很小" |
| 2025-06-12 | Cognition《Don't Build Multi-Agents》 | 两条原则：共享上下文与完整轨迹；动作携带隐性决策。默认推荐单线程线性 agent |
| 2025-06-13 | Anthropic《How we built our multi-agent research system》 | 同一周给出反面证据：Opus 4 当 lead + Sonnet 4 当子代理，比单 Opus 4 高 90.2%；同时承认多 agent 约为聊天 15 倍 token |
| 2026-04 | Cognition《Multi-Agents: What's Actually Working》 | 修正而不推翻：写操作保持单线程时，多 agent 确实能跑；给出代码审查循环、跨模型路由等已落地模式 |

两篇文章不矛盾，它们描述的是两种负载。Anthropic 的检索任务几乎全是读——搜网页、看文档、抓事实，子任务之间不共享可变状态，隔离几乎纯赚。Cognition 的编码任务是密集的写——每一处编辑都要和其他编辑保持风格与边界一致，隔离恰好把最需要共享的决策切断了。

Cognition 在 2026 年的复盘里补了一条很有用的实证：让审查 agent 用**完全干净的上下文**去审代码，效果比带着写代码时的推理过程去审更好。Devin Review 平均每个 PR 抓出 2 个 bug，其中约 58% 属严重级别（逻辑错误、缺失边界、安全漏洞）。干净上下文反而更敢说真话，这一条对内容复查同样成立。

### 3.4 一条能落地的判据

**读出并发，写入串行。**

判断一个任务适不适合拆团队，数一下有多少比例的步骤满足"只读、彼此不依赖"：

- 素材检索、竞品扫描、多源核实、代码搜索、读文档 → 可以并行，最坏结果是取到重复数据。
- 写文件、提交代码、发消息、定规范、改统一风格 → 必须串行，两个人同时写同一份产物就是互相覆盖。

Anthropic 的研究系统落在这条线上：子代理只读（搜、抓、筛），lead 只写（合成报告、跑引用校验）。它算 Cognition 原则的一个实例，而非反例。

### 3.5 成本与失败模式

- **token**：单个 agent 约为普通对话的 4 倍，多 agent 约 15 倍。Anthropic 自己的说法是，多 agent 只适合"任务价值高到付得起这份溢价"的场合。
- **性能归因**：Anthropic 分析 BrowseComp 时发现，token 用量单独就解释了 80% 的性能方差，工具调用次数和模型选择是另外两个因素，三者合计解释 95%。换句话说，多 agent 主要靠"花掉更多 token 去想"取胜，架构本身不产生智力。
- **失败分布**：MAST 把 14 种失败模式归成系统设计问题、成员间错位、任务验证缺失三类。多数翻车出在角色边界不清、缺中间验证环节、成员目标错位，与模型能力关系不大。
- **同预算下的反证**：Tran 与 Kiela（2026-04）用数据处理不等式给出理论论证——在固定推理 token 预算、且上下文利用充分时，单 agent 在信息效率上占优；只有在单 agent 的有效上下文利用率下降、或投入更多算力时，多 agent 才能追平。他们在 Qwen3、DeepSeek-R1-Distill-Llama、Gemini 2.5 三个模型家族上做了控制实验，结论是等预算下单 agent 在多跳推理上稳定打平或超过多 agent。文章还指出 API 侧的预算控制（尤其 Gemini 2.5）和通用基准本身都会放大 MAS 的表面增益。

这一条把前面的"token 归因"顶到了理论层面：多 agent 的优势大部分可以用"没算账的算力"解释，架构本身的信息效率更低——因为每次在 agent 之间转交，只能丢信息，不能加信息。

## 4. 具体应用场景

### 4.1 Anthropic 的 Research 功能（一手案例）

- **输入**：用户一句开放式问题，比如"找出标普 500 信息技术板块所有公司的董事会成员"。
- **怎么跑**：LeadResearcher 先想方案、把计划写进外部记忆（上下文超 20 万 token 会被截断），再派生 3—5 个子代理并行搜；子代理用交错思考评估结果、只回传要点；lead 判断够不够，不够再派；最后由独立的 CitationAgent 做引用定位。
- **为什么用它**：这类广度优先的检索没法预先写死路径，单 agent 顺序搜会慢到跑不完。
- **规模怎么定**（官方给的规则）：简单事实核查 1 个 agent、3—10 次工具调用；直接对比 2—4 个子代理、每个 10—15 次；复杂研究 10 个以上子代理、职责明确分开。

### 4.2 用 WorkBuddy Agent Teams 搭一支内容生产团队

按你手上「小鱼学新传」这条线，一个合理的切法是：

| 角色 | 职责 | 读/写 |
|---|---|---|
| 主编（lead） | 选题四问判定、定框架与角度、统稿、最终发布决定 | 写（唯一） |
| 侦察 | 扫榜、筛候选、产出候选清单 | 只读 |
| 核查 | 出事实卡片：日期、主体全称、数字、有无反转 | 只读 |
| 渲染 | HTML → 1080×1440 PNG，负责自己那套文件 | 写（各自独立文件） |
| 复查 | 禁用句式、口径、红线、标题三处一致性 | 只读 |

三条操作要点：

1. **写的人只有一个，或者每人负责不同文件集合**。官方文档明确警告两个成员同时编辑同一文件会互相覆盖。图卡这种五页 HTML 一人一套目录，天然可以并行。
2. **初始 prompt 必须自包含**。成员看不到 lead 的对话历史，也不会自动知道你上一期做过什么。选题、编号、模板版本、禁用句式清单得直接写进去。
3. **用委派模式管住 lead 的手**。按 Shift+Tab 切到委派模式后，lead 只能用协调类工具，不能自己读文件改代码，防止它抢着干成员的活导致并行失效。

护栏（官方口径）：一个会话只能管一个团队，不支持嵌套团队，每个频道 2—6 名成员，整体处于实验阶段，`/resume` 不恢复成员。

## 5. 容易混淆的概念辨析

| 概念 | 谁决定下一步 | 上下文 | 成员能不能互通 | 适合什么 |
|---|---|---|---|---|
| 多 agent 团队 | lead 拆解 + 成员自主认领 | 每个成员独立，隔断 | 能，有信箱/频道 | 需要讨论、并行探索、跨层协作 |
| 子代理 subagent | 主代理 | 独立窗口，结果回传主代理 | 不能，只能向主代理汇报 | 聚焦型子任务，只要最终结果 |
| 工作流 workflow | 代码写死的图 | 可共享 | 由代码决定 | 路径固定、要可复现 |
| 单 agent 多次采样投票 | 无，同一 agent 采样 N 次 | 各自独立 | 不通信 | 有明确答案的题，成本换准确率 |
| 专家 / 技能（Expert、Skill） | 当前这个 agent | 同一个 | 不涉及 | 换方法论、换人格，不换执行主体 |

一句话区分：**子代理是"派个跑腿的"，团队是"开个会"，工作流是"流水线"，多采样是"多抛几次硬币"。**

## 6. 使用边界 / 常见误区

**四个高频误区**

1. **人多力量大**。《More Agents Is All You Need》用纯采样投票把 agent 数量放大，性能呈倒 U 形——超过阈值后冗余候选反而稀释投票有效性。同质叠加有边际递减，MacNet 能做出 S 形增长靠的是有向无环图给的拓扑位置，不是数量本身。
2. **让成员自由群聊就能涌现协作**。MetaGPT 用"传话游戏"论证过：纯自然语言多轮传递必然失真，角色之间还会用闲聊消耗 token。它的解法是让每个角色产出 schema 化的文档，交接只认文档。
3. **把多 agent 当质量保险**。MAST 的结论正好相反：失败集中在协作结构，加人不会修好结构问题，只会放大它。
4. **让两个成员并行写同一份产物**。这是最昂贵也最常见的错，症状是产出"每段都合理、整体不协调"。

**什么情况下别拆**

- 任务顺序强依赖，后一步要用前一步的隐性判断（多数改稿、多数多文件重构）。
- 子任务需要共享同一份未写下来的风格约定。
- 任务价值撑不起 15 倍 token。
- 一个会话、一次对话就能收尾。

**上手前的五问清单**

1. 这活里有多少比例是"只读且互不依赖"的？低于一半就别拆。
2. 谁能写？写的人是不是只有一个？
3. 成员交回来的东西长什么样？有没有固定格式（卡片、表格、清单）？
4. 中间要不要设验证点？谁验？
5. 出错的代价，和 15 倍成本比，哪个更贵？

## 7. 自测问题

**Q1** 一篇同周发布的文章说多 agent 提升 90.2%，另一篇说别建多 agent。这两者冲突吗？

<details>
<summary>答案</summary>

不冲突，负载不同。Anthropic 的检索任务以读为主、子任务弱耦合，隔离几乎纯赚；Cognition 的编码任务以写为主、决策强耦合，隔离切断了必须共享的隐含决策。判据是读/写比例，不是谁对谁错。
</details>

**Q2** 为什么说多 agent 的收益主要来自 token 消耗，这个说法会带来什么策略含义？

<details>
<summary>答案</summary>

Anthropic 在 BrowseComp 上的归因显示 token 用量单独解释 80% 的性能方差。含义是：如果能用更便宜的方式（更好的模型、更长的单 agent 循环、更精准的检索）花掉同样的 token，未必需要多 agent。多 agent 是"扩容上下文与并行度"的手段之一，成本最高。Tran 与 Kiela（2026-04）把这一点推到理论层：预算对齐后单 agent 在多跳推理上持平或更优，说明 MAS 的信息效率本身更低。
</details>

**Q3** 团队里五个人，四个只读一个写，和一个 lead 带四个只读子代理，区别在哪？

<details>
<summary>答案</summary>

通信拓扑和自主性。团队成员之间有信箱、能互相发消息、能自主认领任务，可以辩论；子代理只能向主代理汇报，彼此不知道对方在干什么。前者协调开销更高，换取的是交叉质疑和动态分工。任务需要"成员互相推翻对方假设"时才值得升级到团队。
</details>

**Q4** 让 lead 自己动手写图卡，会破坏什么？

<details>
<summary>答案</summary>

破坏并行结构：lead 一边写一边等，成员的产出可能白做，且 lead 的上下文被具体实现细节占满，失去统稿视角。这就是委派模式存在的理由——限制 lead 只用协调工具。
</details>
